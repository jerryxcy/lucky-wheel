# Shared Wheel persistence uses Spring Data JPA

Shared Wheel relational state is mapped with Spring Data JPA and Hibernate, using repositories, transaction boundaries, and optimistic versioning without Lombok. ADR-0001 rejected JPA when the server had no persistent resources; optional Shared Wheels introduce exactly the cross-table state and transactional lifecycle that make an ORM useful, so that earlier rationale no longer applies to this mode. Current members and eligibility are normalized relational rows so database constraints can protect the mutable roster, while each immutable Spin record stores its ordered eligible-member and complete draw-order snapshots as PostgreSQL `jsonb`; those lists are retrieved whole and have no member-based query requirement in the MVP. A Shared Wheel remains the concurrency root: member or Spin-record entity changes must not be assumed to increment its version implicitly, and integration tests must prove that every aggregate mutation advances and checks the wheel version. Each command's application-service method owns the transaction that loads and validates the aggregate, writes all state changes, and flushes before returning; controllers do not own transactions, and shared events are published only after a successful commit.
