# SSE invalidates Shared Wheel state

Shared Wheel mutations use REST, while Server-Sent Events notify connected browsers after a transaction commits that a newer wheel version exists. State-change events identify the committed version and, for a completed spin, its spin ID; a terminal wheel-deleted event instead says that no authoritative version remains. Clients use `GET` to refresh the authoritative snapshot and locally reveal the committed draw order. A `409 Conflict`, initial load, reconnect, window focus, or SSE notification all use the same refresh path, so SSE is not the sole source of truth. Only a newly received committed-spin event starts a reveal: initial loads and reconnects show the latest result without replaying an old animation, and an interrupted reveal resumes as the complete result rather than from an animation frame. During a reveal, the client freezes that Spin record's playback and coalesces ordinary invalidations into one refresh after the animation; if a newer Spin then exists it shows that result complete with a notice instead of replaying every missed animation. A wheel-deleted event interrupts the reveal immediately. Reveal disables controls only in each browser that is playing it; the server does not persist a spinning state, guess an animation deadline, or hold the aggregate until clients finish or skip playback. Delivery is deliberately best effort: there is no transactional outbox or guaranteed replay between the database commit and in-process publication, and a missed notification is recovered by a later refresh. This provides near-real-time projected updates without WebSocket complexity or frame-level animation synchronization; missed events may delay the display but cannot fork persisted state.
