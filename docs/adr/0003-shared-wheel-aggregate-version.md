# Shared Wheel uses aggregate-level optimistic concurrency

Every Shared Wheel has one version shared by all of its state, and every mutation must identify the version it expects to change. A stale mutation is rejected with `409 Conflict` rather than merged, retried, or silently applied to newer state; the client refreshes the authoritative wheel state and asks the user to retry intentionally. Mutable configuration is replaced through one aggregate `PUT` containing the complete name, auto-remove setting, members, and eligibility, while server-owned Spin records cannot be supplied through that representation. This keeps the API small and matches the deliberately coarse conflict boundary; sending the complete roster is acceptable under the 100-member limit. A PUT whose expected version is current but whose representation is identical is a no-op: it does not advance the version, extend retention, or publish an event. Every committed spin advances the wheel version even when auto-remove is disabled because it creates a Spin record, changes the latest result, extends retention, and triggers a shared reveal; concurrent spins never both succeed from the same version. Commands use PostgreSQL's default `READ COMMITTED` isolation together with the aggregate version rather than adding `SERIALIZABLE` isolation and a second retry mechanism. The boundary prevents concurrent spins and roster, eligibility, or setting changes from producing inconsistent records while keeping database transactions short; conflicts between otherwise independent member changes are an accepted MVP trade-off. Database constraints still protect structural invariants, but a locks table, uniqueness constraints alone, and per-member versions do not replace the wheel-level version because a spin depends on the aggregate's complete eligible state.
